Read me first

A plain-English guide to what was found by clicking through Zoho ERP Settings in a trial account.

How to use: pick a page in the left menu. It follows the same order as Zoho's own Settings menu. Every page answers four questions: what is it, what do I see, what call goes to the server, what errors can I hit (split into screen errors and server errors).

The company card: name, logo, address, currency, financial year and date format.

How a click reaches the backend

One simple path every call follows. Steps marked inferred are guesses about the hidden part.

Step by step

  • 1. You click or open a page. The browser sends a call to erp.zoho.in/api/<version>/... with your sign-in cookie and the organisation id. (observed)
  • 2. The front door (gateway or edge layer, server name "ZGS") checks your session and counts your calls. (observed headers, role inferred)
  • 3. On a write, the call also carries a security token (x-zcsrf-token), your role id (x-role-id) and the page build (x-zb-asset-version). The server checks your role. (observed)
  • 4. The ERP service checks the rules. If one fails you get 400 with a sentence. (observed)
  • 5. It reads or writes the data. The database engine is not visible from outside. (inferred)
  • 6. The answer comes back as JSON {code, message, data}. After a write, the page usually asks for the list again, which is a second read. (observed)
  • 7. When the page itself hits a JavaScript error it reports it: POST v3/errors (HTTP 201) with a form body url, browser (the browser string), ember_version (3.28.10 seen), build_label and trace (the stack text). The front end is therefore an Ember app. This was seen while forms were driven by script, so ordinary use may report less. (observed)

  • 2. It opens a TLS connection. In a test: connect 51 ms, TLS finished at 108 ms, certificate verified. Public replies came over HTTP/1.1.
  • 3. The front door is the Zoho gateway. Every reply says Server: ZGS and sets a load balancer cookie named zalb_<hex> that pins you to one back end. A JSESSIONID cookie also appears on a first visit, so the back end is Java.
  • 4. The gateway passes the call to the right service by path: /api/v3 (ERP), /api/v1 with request_service=payroll or expense (those apps run in same-origin frames), /api/v4 (payment terms).
  • 5. The service checks the sign-in cookie, the x-zcsrf-token header, the organization_id and the x-role-id, then reads or writes the database and answers { code, message, data }.
  • 6. Client JavaScript errors are sent back with POST v3/errors.

How errors look to the user

  • Browser checks come first: a red banner inside the dialog, no request sent.
  • Server refusals show the server's own sentence in a red banner at the top of the form.
  • Success: a green toast ("Theme preference has been saved.") or the list simply updates.
  • Confirmations are in-app dialogs, not browser pop-ups.
  • Slow saves show a spinner and a disabled Save button (role save: about 10 s).
  • The form keeps what you typed after an error.
